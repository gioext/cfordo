# cfordo

[日本語](README.ja.md)

## Purpose

A TypeScript framework for executing predefined workflows with Cloudflare Workflows, Queues, and D1.
Define bindings, steps, and business logic in a class that extends Ordo. cfordo handles queue delivery, completion notifications, result storage, validation, evaluation, and retries.

AI-generated changes to workflow steps, changes to steps during execution, and deployment outside Cloudflare are out of scope.

## Specification

### Usage

```ts
import { Ordo, type OrdoContext } from "cfordo";

export class MyWorkflow extends Ordo<Env> {
  async setup() {
    this.binding({
      db: this.env.DB,
      queue: this.env.JOBS,
      workflow: this.env.FLOW,
    });
    this.configure({
      expiresIn: 24 * 60 * 60 * 1000,
    });
    this.step({
      name: "calculate",
      run: this.double,
      validate: this.validateDouble,
      evaluate: this.evaluateDouble,
    });
  }

  async double(ctx: OrdoContext) {
    const params = ctx.params<{ value: number }>();
    return { value: params.value * 2 };
  }

  async validateDouble(ctx: OrdoContext) {
    if (ctx.result().value < 0) return ctx.ng("The result is negative");
    return ctx.ok();
  }

  async evaluateDouble(ctx: OrdoContext) {
    // This example uses a numeric comparison. Call your AI evaluator here if needed.
    if (ctx.result().value !== ctx.params().value * 2) {
      return ctx.ng("The result does not equal twice the input");
    }
    return ctx.ok();
  }
}

export default MyWorkflow;
```

Use the binding types generated by Wrangler for `Env`. Ordo does not require type arguments for business data.
Set Wrangler's `class_name` to the exported Workflow class name: `MyWorkflow` in this example.
The named class export exposes the Workflow, and the default export exposes the Queue consumer.

Start a Workflow by calling `create()` on its Workflow binding from your HTTP API, scheduled handler, or another entry point.
cfordo implements the `run(event, step)` entry point called by Cloudflare. Your class provides `setup()` and the business methods.

### Using Hono

To combine the Queue consumer with an HTTP handler, replace the final default export:

```ts
import { Hono } from "hono";
const app = new Hono();

export default {
  fetch: app.fetch,
  queue: MyWorkflow.queue(),
};
```

`MyWorkflow.queue()` returns a Queue event handler. Calling it does not create an instance, invoke `setup()`, or perform I/O.
Each incoming Queue event creates a fresh instance using that event's `env` and execution context.
The Workflow and Queue consumer use the same class definition, but do not share instances or execution state.

### Initialization and bindings

`setup()` is a required asynchronous method. TypeScript reports a missing implementation. The `override` keyword is not required.
It runs once per instance, before the first Workflow or Queue operation.
It runs after class fields have been initialized, so it can access `this.env` and your own fields.
Concurrent initialization requests on the same instance do not run `setup()` more than once.
An instance whose initialization fails does not start processing.

Use `setup()` to register bindings, settings, and steps. New instances invoke it again, including instances created for Workflow resumption or other Queue events. Put business side effects in step handlers such as `run`.

`this.binding()` is required. Supply all three bindings together, once:

| Key | Required | Purpose |
|---|---|---|
| `db` | Yes | D1 binding for execution state and results |
| `queue` | Yes | Queue binding for sending step execution requests |
| `workflow` | Yes | Workflow binding for completion notifications after results are saved |

The type system checks that all three bindings are provided. A missing `binding()` call or invalid bindings also cause an error before business logic starts.
Specify the Queue and notification destination for the Ordo instance once; individual steps do not repeat the bindings.
If one consumer serves multiple Ordo classes, your application selects the appropriate handler for each Queue.

`this.configure()` is optional and accepts the following execution setting:

| Key | Required | Purpose |
|---|---|---|
| `expiresIn` | No | Goal lifetime in milliseconds, as a positive integer. Defaults to 24 hours. |

A Goal represents one workflow run.
Registration does not access the database or send Queue messages. Processing starts only after `setup()` succeeds and the settings and steps have been checked.
Settings and steps cannot be changed after execution starts.

### Steps

`this.step()` accepts one object. Its return value is not used.

| Key | Required | Purpose |
|---|---|---|
| `name` | Yes | Step name |
| `run` | Yes | Asynchronous method or function that performs business logic and returns a result |
| `validate` | No | Asynchronous method or function that checks business rules |
| `evaluate` | No | Asynchronous method or function that evaluates whether the result is acceptable |

Registered methods execute with `this` bound to their Ordo instance. You do not need to call `.bind(this)` yourself.
Business logic, validation, and evaluation can use `this.env` and shared methods on the class.
The same method can be reused by multiple steps, with validation and evaluation specified separately for each step.
There is no separate Worker registration or string-based reference to a business handler.

Ordinary steps execute in registration order. The Goal completes when the final step succeeds.
Steps registered inside an asynchronous `this.parallel()` callback execute in parallel. This callback is also bound to the same instance.

```ts
async setup() {
  this.binding({ db: this.env.DB, queue: this.env.JOBS, workflow: this.env.FLOW });
  this.configure({ expiresIn: 24 * 60 * 60 * 1000 });
  await this.parallel(this.registerParallel);
}

async registerParallel() {
  this.step({ name: "first", run: this.double, validate: this.validateDouble, evaluate: this.evaluateDouble });
  this.step({ name: "second", run: this.double, validate: this.validateDouble, evaluate: this.evaluateDouble });
}
```

Execution proceeds to the next stage only after every parallel step succeeds. Retrying a failed step does not rerun its successful siblings.
Duplicate step names, empty parallel groups, and nested parallel groups are not allowed.
Await asynchronous registration in `setup()`. Business logic does not start if there are no steps or the definition is invalid.

### Shared context and return values

Business logic, validation, and evaluation each receive one `OrdoContext`.

| API or value | Description |
|---|---|
| `ctx.params<T>()` | Parameters supplied when the Goal starts. Defaults to `any` when no type argument is provided. |
| `ctx.result<T>()` | Business result being validated or evaluated. Defaults to `any` when no type argument is provided. Returns `undefined` during business execution. |
| `ctx.goalId` | Goal ID |
| `ctx.stepName` | Name of the executing step |
| `ctx.attemptId` | ID identifying one attempt to execute a step |
| `ctx.feedback` | Reason for a previous failed check: `{ source: "validate" or "evaluate", reason: string }`. Absent on the first execution. |
| `ctx.ok()` | A successful validation or evaluation. Takes no arguments. |
| `ctx.ng(reason)` | A failed validation or evaluation. Requires a reason containing at least one non-whitespace character. |

Type arguments to `params()` and `result()` provide static types only. They do not validate or transform values at runtime.
Changing retrieved data does not modify the saved input or result.
Input/output schemas and separate `Input` or `Output` type definitions are not required.

Business handlers return their results with an ordinary `return`; they do not use `ctx.ok(result)`.
Inputs and results must be serializable as JSON. A `null` result is allowed, but a missing return value, `undefined`, circular references, and non-finite numbers cause errors.
cfordo does not validate the fields or types of business data. It does not provide an `output` schema option or integration with Zod or Standard Schema.

Validation and evaluation must return `ctx.ok()` or `ctx.ng(reason)` from the context passed to that call.
Arbitrary objects, booleans, missing return values, and decisions created by another invocation are not accepted.
An invalid return value is treated as an exception in the check function, not as a negative verdict.
Reasons for negative verdicts are saved and passed to the next execution through `feedback`.
Your application defines any AI models, prompts, tools, and related logic.

### Execution guarantees

- Business logic runs first, followed by validation and evaluation when provided.
- Results and check history are saved in D1. No completion notification is sent if saving fails.
- If notification fails after saving, the saved result is used to send the notification again.
- Queue redelivery does not repeat business logic or validation whose results have already been saved.
- Duplicate completion notifications do not repeat evaluation or subsequent steps.
- If validation or evaluation throws an exception, only the failed check is retried.
- A negative verdict restarts the same step from its business handler, with the reason supplied as feedback.

Across the entire execution of a given Goal and step, the fixed limits are 3 attempts for exceptions, 3 for negative validation verdicts, and 10 for negative evaluation verdicts. All limits include the initial attempt.
The counters are independent and are not reset when the step is launched again. Reaching a limit fails the Goal and prevents subsequent steps from starting.

The Workflow returns `completed` on success, `failed` on failure, or `expired` when it detects that the Goal has expired.
Failures in `setup()` or configuration checks raise errors before a Goal is created. If the execution platform stops processing, the Workflow may be unable to return a value.
The expiration time is fixed when the Goal starts and is not extended by retries. Completed or failed Goals retain their status after the expiration time.
The database is not updated solely to mark expiration.
After detecting expiration, cfordo does not start new steps, retries, or evaluations. It does not guarantee that business logic already in progress will stop at the exact expiration time.

The management database is initialized and migrated automatically when Workflow or Queue processing starts. Business logic does not start if initialization fails.
You can call `initOrdo(env.DB)` to initialize it explicitly. Your application decides how to store business data and external content.

## Development environment

Use the Node.js and pnpm versions specified in `mise.toml`. Type checking uses `tsrs`; Cloudflare runtime tests use Wrangler and Miniflare.
Generate application binding and runtime types with `wrangler types`.

## Development

```sh
mise install
pnpm install --frozen-lockfile
pnpm check
pnpm build
pnpm --filter @cfordo/example typecheck
```

`pnpm test` checks the public API types, configuration, registration, verdicts, execution control, and database behavior. It also runs integration tests for Workflows, Queues, D1, and Hono in the Workers runtime.
Tests do not deploy to Cloudflare or call external AI APIs.
`pnpm build` writes ESM JavaScript, type declarations, and source maps to `dist`.

## Deployment

To publish the npm package, use an account with publishing permission:

```sh
pnpm run deploy
```

Type checking, tests, and a build run before publication.
Deploy consuming Workers with Wrangler and configure D1, the Queue producer and consumer, and the Workflow binding.
Manual initialization of the management database is not required.
